01 — ปัญหาและที่มา

ทำไมต้องมีระบบนี้

จุดตั้งต้นคือช่องว่างสองเรื่องที่เกิดขึ้นพร้อมกันในระบบสาธารณสุขไทย

ขาดแคลนแพทย์เฉพาะทางหัวใจ — หน่วยบริการปฐมภูมิและ รพ.สต. ต้องอ่าน ECG จำนวนมากโดยไม่มีแพทย์เฉพาะทางประจำ ทำให้เกิดคอขวดในการคัดกรองเบื้องต้น

ข้อมูล ECG ติดอยู่บนกระดาษ — เครื่อง ECG ส่วนใหญ่ในหน่วยบริการยังพิมพ์ผลเป็นกระดาษความร้อน (thermal paper) ที่เสื่อมสภาพตามเวลา ข้อมูลเหล่านี้ไม่เคยถูกแปลงเป็นตัวเลขที่คอมพิวเตอร์ประมวลผลต่อได้ — วิเคราะห์ย้อนหลัง, เทียบเคส, หรือป้อนเข้าโมเดล AI ไม่ได้เลยถ้าไม่ digitize

ระบบ AI แบบเดิมเข้าใจแค่รูปแบบคลื่น — ตรวจจับความผิดปกติจาก pattern บนกราฟ 2 มิติเท่านั้น ไม่มีความเข้าใจว่าสัญญาณไฟฟ้าที่ผิดปกตินั้น "มาจากตำแหน่งไหนในหัวใจจริง ๆ" เชิงพื้นที่สามมิติ

02 — ขอบเขตและจุดยืน

ระบบนี้คืออะไร และไม่ใช่อะไร

กำหนดขอบเขตไว้ชัดเจนตั้งแต่การออกแบบ เพราะเป็นเครื่องมือที่แตะข้อมูลทางคลินิก:

สิ่งที่เป็น

  • เครื่องมือสนับสนุนการตัดสินใจ (Decision Support) และช่วยวิเคราะห์เบื้องต้น เพื่อลดภาระงาน
  • รองรับภาพสแกน/ถ่ายภาพ ECG มาตรฐาน 12-lead
  • รองรับสัญญาณเรียลไทม์ผ่านโมดูล AD8232 (single-lead)
  • จำแนกกลุ่มความผิดปกติหลักด้วยโมเดลที่เทรนจาก PTB-XL
  • ทุกค่าที่วัดไม่ได้จริง จะแสดงเป็น null พร้อมเหตุผล ไม่เดาแทน

สิ่งที่ไม่เป็น

  • ไม่ใช่เครื่องมือวินิจฉัย (Diagnose) หรือสั่งการรักษาแทนแพทย์
  • ไม่ใช่ผลสรุปที่ใช้ได้โดยไม่ผ่านการทบทวนของแพทย์ — ทุกผลลัพธ์ต้องมี clinician sign-off
  • โมดูลระบุตำแหน่งแหล่งกำเนิดไฟฟ้า 3 มิติ (PINN) ยังไม่ผ่านการ validate กับผู้ป่วยจริง — เป็นงานวิจัยที่กำลังพัฒนา

04 — Workflow แบบละเอียด (End-to-End)

จากภาพ/สัญญาณดิบ ไปจนถึงหน้าจอแพทย์

นี่คือลำดับขั้นจริงที่ pipeline ทำงาน ไม่ใช่ผังแบบย่อ — แต่ละขั้นมีเหตุผลว่าทำไมต้องมี และเมื่อล้มเหลวจะรายงานสาเหตุแทนการเดา

0
Input
รับข้อมูลดิบ

ภาพถ่าย/สแกนกระดาษ ECG อัปโหลดผ่าน API หรือสัญญาณจาก AD8232 สตรีมเข้าทาง WebSocket 20 Hz

1
preprocess.py
แก้เรขาคณิตของภาพ (เฉพาะ input แบบภาพ)

ภาพถ่ายจริงมักเอียง/หมุน/มีมุมกล้องเฉียง แก้ตามลำดับนี้:

  • ตรวจการหมุนหยาบ (0/90/180/270°) ด้วย Tesseract OSD — จำเป็นเพราะภาพถ่ายมือถือมักหมุนเต็มมุม ไม่ใช่แค่เอียงเล็กน้อย
  • ปรับมุมมองภาพ (perspective warp) จากมุมกระดาษที่ตรวจพบ
  • ปรับเอียงละเอียด (deskew ±12°) จากทิศทางเส้น grid ด้วย Hough transform
แก้แล้ว: page boundary detection เดิมตัดภาพเหลือ ~44% ของความกว้างจริงเมื่อ ink บนภาพถ่ายจางกว่ารูปสังเคราะห์ — เพิ่มเกณฑ์ยอมรับจาก 35–40% เป็น 65% ของ width ยืนยันด้วยภาพถ่ายเครื่อง Kenz C306 จริง
2
calibration.py
คำนวณมาตราส่วน px → mm

วัดระยะห่างเส้น grid บนกระดาษ (ปกติ 1 มม./ช่อง) เพื่อแปลงพิกเซลเป็นมิลลิเมตร แล้วเป็นเวลา/แรงดันจริง

grid_spacing — วัดได้จริง fallback_width_assumption — เดาจากสัดส่วนหน้ากระดาษ

เมื่อวัดเส้น grid ไม่ได้ (กระดาษถ่ายภาพจริงมักมีเส้นจางกว่า) ระบบจะบอกตรง ๆ ว่า calibration_uncertain: true แล้วส่งค่านี้ต่อไปจนถึงหน้าจอแพทย์ — ไม่ใช่คำนวณค่าลวงแล้วแสดงเหมือนมั่นใจเต็มร้อย

3
layout.py
ตรวจจับโครงสร้างหน้ากระดาษ (Auto-detect Layout)

กระดาษ ECG มีหลายรูปแบบการจัดวาง — ระบบตรวจ 2 รอบ (fixed-region แล้ว adaptive-region) แล้วให้คะแนนความเชื่อมั่นต่อ panel ผ่าน OCR อ่านชื่อ lead ยืนยันตำแหน่งที่คาดไว้

label_confirmed position_inferred label_conflict → ตัดทิ้ง ไม่เดา low_confidence

รองรับ layout: 3×4+1 (มาตรฐาน), 4×3+1, 2×6, multi-strip

แก้แล้ว: calibration pulse (ปุ่มสี่เหลี่ยม ⊓ อ้างอิง 1mV ต้นแถบ) เคยถูก OCR อ่านผิดเป็นตัวอักษร "I" แล้วชนกับป้าย lead จริง ทำให้ทั้ง panel ถูกทิ้ง — เพิ่มเงื่อนไขลดระดับความเชื่อมั่นแทนการทิ้งทันทีเมื่อความขัดแย้งเป็นแค่ 1 ตัวอักษรที่เป็น prefix ของชื่อ lead ที่คาดไว้
4
trace_extract.py
แปลงเส้นกราฟเป็นตัวเลข (Signal Extraction)

ไล่ทีละคอลัมน์พิกเซลในกรอบของแต่ละ lead หาตำแหน่ง ink กึ่งกลาง แล้วแปลงเป็นค่าแรงดัน (mV) ด้วยมาตราส่วนจากขั้นตอนที่ 2 — ตัด calibration pulse ที่ต้นแถบออกก่อน ไม่ให้ปนเป็นสัญญาณคลื่นหัวใจ

ช่องว่างจาก ink ที่จางเกินไป (gap_fraction > 0.35) → ทำเครื่องหมาย low_confidence แทนการเติมข้อมูลเดา

5
header_ocr.py
อ่านหัวกระดาษด้วย OCR

ดึงข้อมูลผู้ป่วย, ค่าที่เครื่องคำนวณเอง (HR/PR/QRS ฯลฯ), และคำแปลผลที่เครื่องพิมพ์ไว้ — เก็บแยกจากค่าที่ระบบคำนวณเอง (machine_reported vs signal_measurements) เพื่อเทียบความสอดคล้องได้ ไม่ปนกัน

6
measurements.py
คำนวณค่าทางคลินิก (HR / PR / QRS / QT / QTc / Axis)

ใช้ neurokit2 หา R-peak แล้ว delineate ขอบ P/QRS/T ต่อ beat — ลองจาก rhythm strip (สัญญาณยาว ~10 วิ) ก่อนเสมอเพราะมีจำนวน beat พอให้ผลเสถียรกว่า short panel (~2.5 วิ) แล้วค่อย fallback

ทุกค่ามาพร้อมเหตุผลเมื่อวัดไม่ได้ หรือเมื่อวัดได้แต่ควรระวัง (calibration_uncertain, image_heuristic_approx, digitization_anomaly) — ไม่มีค่าไหนแสดงแบบเงียบ ๆ โดยไม่ระบุที่มา

7
morphology.py
วิเคราะห์รูปคลื่นราย lead (ST / T / R / P)

ต่างจากขั้นตอนที่ 6 ตรงที่วิเคราะห์แยกทุก lead อิสระต่อกัน — ST-segment elevation/depression ที่จุด J+60ms, ทิศทาง T-wave (ยกเว้น aVR ที่ปกติกลับหัวอยู่แล้ว), R-wave amplitude ใน V1–V6 (poor R-wave progression), P-wave duration/amplitude ใน lead II (atrial enlargement)

8
classifier.py
คัดกรองด้วย AI (PTB-XL Classifier)

ต้องมีครบ 12-lead มาตรฐานเท่านั้นถึงจะรันได้ (classification_eligible) — โมเดล CNN เทรนจากฐานข้อมูล PTB-XL รันผ่าน ONNX runtime ได้ผลเป็นความน่าจะเป็นต่อกลุ่มโรค (NORM / MI / STTC / CD / HYP)

9
EP-PINN + CardiacLocalizer
ระบุตำแหน่งแหล่งกำเนิดไฟฟ้า 3 มิติ

ผสาน Dipole theory เข้ากับโครงข่ายประสาทเทียมแบบ Physics-Informed เพื่อจำลองการแพร่กระจายไฟฟ้าในเนื้อเยื่อหัวใจ (อิงแบบจำลอง Aliev–Panfilov) แล้วหาตำแหน่งเชิงพื้นที่ของสัญญาณผิดปกติ — จุดต่างจากการดู pattern คลื่นแบบเดิมโดยตรง

ข้อจำกัดที่ต้องระบุตรง ๆ

โมเดลส่วนนี้เทรนด้วยข้อมูลจำลอง (simulated data) เท่านั้น ยังไม่ผ่านการ validate กับสัญญาณผู้ป่วยจริง — อยู่ระหว่างวิจัยและพัฒนา ต้องผ่านการเก็บข้อมูลคลินิกภายใต้ IRB และทดสอบทางคลินิกก่อนใช้งานจริง

10
safety_gate.py
ประตูความปลอดภัยทางคลินิก (Safety Gate)

รวมสัญญาณทั้งหมดจากทุกขั้นตอนก่อนหน้า (จำนวน lead ที่กู้คืนได้, ความเชื่อมั่นของ layout, มุมเอียงที่แก้, ความไม่แน่นอนของ calibration, ความมั่นใจของ classifier) แล้วตัดสิน clinical_use_status เดียว:

eligible_for_review repeat_required not_supported
11
React Worklist
ส่งถึงหน้าจอแพทย์

แสดงคิวผู้ป่วยเรียงตามความเสี่ยงที่ AI ประเมิน, overlay จุดที่ตรวจพบความผิดปกติทับบนกราฟจริง, hover ดูรายละเอียดต่อ lead, และบันทึก audit trail ทุกครั้งที่แพทย์ทบทวน/ตัดสินใจ — ระบบไม่ปิดเคสเองโดยไม่มีแพทย์ลงชื่อ

05 — เทคนิคเชิงลึก

วิธีการที่ใช้ในแต่ละส่วน

Computer Vision

การแปลงภาพกระดาษเป็นสัญญาณดิจิทัล

แยกภาพเป็น 3 มาสก์ด้วยเกณฑ์สี — เส้น grid (ชมพู/แดง), หมึกลายเส้น (ดำ/เทาเข้ม), และรอยปากกาสีน้ำเงินของแพทย์ (แยกออกเพื่อไม่ให้วงกลมที่แพทย์เขียนไว้กลายเป็นข้อมูลคลื่น) จากนั้นหาขอบเขตหน้ากระดาษจาก block ต่อเนื่องที่มีความหนาแน่นของเส้น grid สูงสุด ก่อนตัดแบ่งเป็น panel รายเส้นตาม layout ที่ตรวจพบ

Signal Processing

การวัดค่าทางคลินิกแบบ Honesty-First

ใช้ไลบรารี neurokit2 หา R-peak และ delineate ขอบเขต P/QRS/T ต่อ beat แล้วรวมด้วยค่ามัธยฐาน (median) ข้าม beat เพื่อลดผลกระทบจาก beat ที่ผิดปกติเดี่ยว ๆ ทุกค่าที่ได้จะถูกตรวจสอบย้อนกลับไปยังคุณภาพของ digitization ต้นทาง (จำนวน lead ที่กู้คืนได้, ความไม่แน่นอนของมาตราส่วน) ก่อนแสดงผล — หลักการคือ ไม่มีค่าไหนถูกแสดงราวกับมั่นใจ ถ้าที่มาของมันไม่มั่นใจจริง

Deep Learning

PTB-XL Anomaly Classifier

โมเดล CNN เทรนบนฐานข้อมูล PTB-XL (ฐานข้อมูล ECG มาตรฐานสากล 12-lead) เต็มชุด 17,418 รายการ ผ่านการ sweep hyperparameter 44 รอบ วัดผลด้วย Held-out validation — แยกชุดข้อมูลทดสอบออกจากชุดเทรนตั้งแต่ต้น เพื่อวัดว่าโมเดล generalize ได้จริง ไม่ใช่แค่จำข้อมูลที่เห็น ได้ macro-AUC 0.9245 export เป็น ONNX เพื่อรันบน backend โดยตรง

Physics-Informed Neural Network

EP-PINN + CardiacLocalizer

ผสานสมการฟิสิกส์เข้าไปเป็นส่วนหนึ่งของ loss function ของโครงข่ายประสาทเทียมโดยตรง (ไม่ใช่แค่เรียนจากข้อมูลอย่างเดียว) — อิงแบบจำลองไฟฟ้าเนื้อเยื่อหัวใจ Aliev–Panfilov ร่วมกับ Dipole theory เพื่อให้โมเดลเรียนรู้ตำแหน่งแหล่งกำเนิดไฟฟ้าเชิงพื้นที่สามมิติจากสัญญาณพื้นผิว (12-lead) ปัจจุบันเทรนและทดสอบด้วยข้อมูลจำลองเท่านั้น เป็นส่วนที่ยังอยู่ระหว่างการวิจัย

Hardware

AD8232 Real-time Integration

โมดูลเซนเซอร์ AD8232 (ราคาประมาณ 300–500 บาท) เชื่อมต่อผ่าน USB serial ระบบ auto-detect พอร์ตอุปกรณ์ทั่วไปได้เอง สตรีมสัญญาณ single-lead ผ่าน WebSocket ที่ 20 Hz เข้าสู่ pipeline การวัดค่าเดียวกับที่ใช้กับภาพ ECG

ปัญหา: ภาพถ่ายจากมือถือมักหมุนเต็ม 90/180/270 องศา (ถ่ายกระดาษวางบนโต๊ะ ไม่ตั้งกล้องตรง) ซึ่งเป็นคนละปัญหากับ "เอียงนิดหน่อย" — ถ้าใช้ตัวแก้เอียงละเอียด (deskew ที่ clamp ไว้แค่ ±12°) จะแก้มุมแบบนี้ไม่ได้เลย ต้องมีตัวตรวจจับแยกที่ทำงานได้เต็ม 360°

def _detect_gross_rotation_deg(rgb: np.ndarray) -> int | None:
    # ใช้ Tesseract OSD (Orientation and Script Detection) —
    # อ่านทิศทางของ "ตัวอักษร" ในภาพ ไม่ใช่เดาจากรูปทรงกระดาษ
    try:
        import pytesseract
        from PIL import Image

        osd = pytesseract.image_to_osd(Image.fromarray(rgb), output_type=pytesseract.Output.DICT)
        confidence = float(osd.get("orientation_conf", 0.0))
        rotate = int(osd.get("rotate", 0))
    except Exception:
        return None  # OCR ล้มเหลว → ไม่เดา ปล่อยผ่าน
    if confidence < 1.5 or rotate not in (90, 180, 270):
        return None  # มั่นใจไม่พอ → ไม่เดา
    return rotate

2. หาขอบเขตหน้ากระดาษจริงในภาพ (Page Boundary Detection)

ปัญหา: ภาพถ่ายมีทั้งกระดาษ ECG และพื้นหลัง (โต๊ะ, มือ, สิ่งของ) ต้องหาว่าพิกเซลช่วงไหนคือ "หน้ากระดาษจริง" — นี่คือจุดที่เจอบั๊กจริงระหว่างพัฒนา: การตรวจจับเดิมตัดภาพเหลือแค่ ~44% ของความกว้างจริงเมื่อทดสอบกับภาพถ่ายจริง เพราะเกณฑ์ความกว้างที่ยอมรับหลวมเกินไป

def _find_widest_contiguous_block(active: np.ndarray) -> tuple[int, int]:
    # active คือ array True/False ต่อคอลัมน์ (หรือแถว) ว่ามี "เนื้อหา" หนาแน่นพอไหม
    # หา "ช่วงต่อเนื่อง" ที่ยาวที่สุดของ True — นั่นคือขอบเขตหน้ากระดาษที่คาดว่าใช่
    blocks = []
    start = None
    for idx, val in enumerate(active):
        if val and start is None:
            start = idx
        elif not val and start is not None:
            blocks.append((start, idx - 1))
            start = None
    if start is not None:
        blocks.append((start, len(active) - 1))
    if not blocks:
        return 0, len(active) - 1
    return max(blocks, key=lambda b: b[1] - b[0])

# ...หลังหา block ที่กว้างที่สุดแล้ว ต้องเช็คว่า "กว้างพอจะเชื่อได้จริง" ไหม:
if (x1 - x0) < width * 0.65 or (y1 - y0) < height * 0.35:
    return None  # แคบเกินไป ไม่น่าเชื่อ → ให้ตัวสำรองทำงานต่อแทน

3. คำนวณมาตราส่วนพิกเซล→มิลลิเมตร จากเส้น grid

ปัญหา: ต้องรู้ว่า 1 พิกเซลในภาพเท่ากับกี่มิลลิเมตรจริงบนกระดาษ ถึงจะแปลงตำแหน่งกราฟเป็นเวลา (วินาที) และแรงดัน (mV) ได้ วิธีที่แม่นที่สุดคือวัดระยะห่างจริงของเส้น grid บนกระดาษ (ปกติห่างกัน 1 มม./ช่อง)

def _estimate_spacing(mask: np.ndarray) -> float | None:
    # หาตำแหน่ง "เส้น" กลาง ๆ ทั้งแนวตั้งและแนวนอน แล้ววัดระยะห่างระหว่างเส้นที่ติดกัน
    col_centers = _line_centers(mask.sum(axis=0).astype(np.float32))
    row_centers = _line_centers(mask.sum(axis=1).astype(np.float32))
    diffs: list[float] = []
    for centers in (col_centers, row_centers):
        if len(centers) < 6:
            continue  # เส้นน้อยเกินจะเชื่อถือความเป็นคาบ (periodicity) ไม่ได้
        local = np.diff(np.asarray(centers, dtype=np.float32))
        local = local[(local >= 3) & (local <= 40)]  # กรองค่าที่ไม่ใช่ spacing จริง
        diffs.extend(float(x) for x in local)
    return float(np.median(diffs)) if diffs else None

def calibrate_grid(grid_mask, page_bbox) -> CalibrationReport:
    spacing = _estimate_spacing(grid_mask[y0:y1, x0:x1])
    if spacing is None or not (3 <= spacing <= 30):
        # วัดเส้น grid ไม่ได้จริง → ประกาศตรง ๆ ว่า "ไม่แน่ใจ" แทนเดา
        return CalibrationReport(
            px_per_mm=(x1 - x0) / 250.0,  # เดาแบบระบุที่มาชัดเจน
            source="fallback_width_assumption",
            calibration_uncertain=True,
            reason="grid_spacing_unavailable",
        )
    return CalibrationReport(px_per_mm=spacing, source="grid_spacing", calibration_uncertain=False)

4. ตัด Calibration Pulse ออกจากสัญญาณ

ปัญหา: กระดาษ ECG จริงพิมพ์ปุ่มสี่เหลี่ยม (⊓) อ้างอิง 1mV ไว้ต้นแถบเสมอ ถ้าไม่ตัดออก ปุ่มนี้จะถูกนับเป็น "คลื่นหัวใจ" ปลอม ๆ ทำให้แกนเวลาเพี้ยนทั้งเส้น

def _skip_leading_calibration_pulse(ys: np.ndarray, max_search_frac=0.20, min_plateau_run=14) -> int:
    # calibration pulse มีลักษณะเฉพาะ: พุ่งขึ้นเร็ว แล้ว "คงที่" (plateau) ต่อเนื่อง
    # ต่างจากคลื่นหัวใจจริงที่ขยับต่อเนื่องแทบตลอดเวลา แม้แต่ช่วง ST ที่ดู "แบน"
    n = ys.size
    search_end = min(n, int(n * max_search_frac))  # หาแค่ 20% แรกของแถบเท่านั้น
    vals = ys[:search_end]

    run_start = 0
    last_plateau_end = None
    for i in range(1, len(vals) + 1):
        broke = i == len(vals) or abs(vals[i] - vals[run_start]) > 1.6
        if broke:
            if i - run_start >= min_plateau_run:  # คงที่นานพอ = plateau จริง
                last_plateau_end = i - 1
            run_start = i
    if last_plateau_end is None:
        return 0  # ไม่เจอ plateau ก็ไม่ตัดอะไร
    return min(n - 1, last_plateau_end + 4)  # ตัดถึงขอบขาลง + กันชนเล็กน้อย

5. ตัดสินระดับความเชื่อมั่นของแต่ละ Panel (OCR + ตำแหน่ง)

ปัญหา: รู้ตำแหน่ง panel แล้ว แต่จะเชื่อได้แค่ไหนว่า panel นี้คือ lead ที่คาดไว้จริง ๆ ต้องผสานหลักฐาน 2 อย่างที่ "ไม่เท่ากัน" — ตำแหน่งที่คาดไว้ (มักถูก) กับสิ่งที่ OCR อ่านป้ายชื่อได้ (บางครั้งผิดเพราะครอปโดนตัวอักษรข้างเคียง)

def _panel_confidence(ink_ok, assumed_lead, matched_lead, conflict_lead, neighbor_leads=()):
    assumed_normalized = _normalize_token(assumed_lead)
    if conflict_lead and conflict_lead != assumed_normalized:
        if conflict_lead in neighbor_leads:
            # OCR อ่านโดนป้ายของ panel ข้างเคียง (ครอปเหลื่อม) ไม่ใช่ label ผิดจริง
            return "low_confidence" if not ink_ok else "position_inferred"
        if len(conflict_lead) == 1 and assumed_normalized.startswith(conflict_lead):
            # ป้ายสั้นแค่ตัวเดียว ("I") ขัดกับป้ายยาวกว่า ("II"/"III")
            # มักเป็น calibration pulse ที่ OCR อ่านผิด ไม่ใช่ label ผิดจริง
            return "low_confidence" if not ink_ok else "position_inferred"
        return "label_conflict"  # ขัดแย้งจริง ไม่เข้าเงื่อนไขพิเศษ → ตัดทิ้ง
    if not ink_ok:
        return "low_confidence"
    return "label_confirmed" if matched_lead else "position_inferred"

Physics-constrained loss function Aliev–Panfilov cardiac EP model Dipole theory
  • ต่างจาก Neural Network ทั่วไปตรงไหน: NN ทั่วไปเรียนรู้แค่จากข้อมูล (input→output) ล้วน ๆ ส่วน PINN ใส่ "สมการฟิสิกส์" เป็นอีกเทอมหนึ่งใน loss function โดยตรง — โมเดลจึงถูกบังคับให้ทำนายคำตอบที่ทั้ง (1) match ข้อมูลจริง และ (2) ไม่ขัดกับกฎฟิสิกส์ที่รู้อยู่แล้ว
  • สมการฟิสิกส์ที่ใช้: แบบจำลอง Aliev–Panfilov อธิบายการแพร่กระจายไฟฟ้าในเนื้อเยื่อหัวใจ ร่วมกับ Dipole theory ที่เชื่อมโยงสัญญาณไฟฟ้าที่วัดได้บนพื้นผิวร่างกาย (12-lead) กลับไปยังตำแหน่งแหล่งกำเนิดในหัวใจ 3 มิติ
  • ทำไมยังเป็น research stage: เทรน/ทดสอบด้วยข้อมูลจำลอง (simulation) เท่านั้น — สมการฟิสิกส์ถูกต้องตามทฤษฎี แต่ยังไม่ผ่านการตรวจสอบว่าคาดการณ์ตำแหน่งได้แม่นบนสัญญาณผู้ป่วยจริงที่มี noise/ความหลากหลายทางกายภาพสูงกว่าข้อมูลจำลองมาก

1D-CNN
เลือกใช้จริง		 Convolution filter สแกนหา local pattern ตลอดเส้นสัญญาณ (weight-sharing) จับรูปร่าง QRS/ST ที่มีลักษณะซ้ำแบบเดิมได้ดี (translation-invariant) พารามิเตอร์น้อย เทรนเร็ว มองความสัมพันธ์ระยะไกลข้ามช่วงเวลาทั้งเส้นได้จำกัดกว่าโมเดลที่มี attention มีตัวเลขจริงรองรับ: val macro-AUC 0.9245 (data-scaling sweep 44 รอบ)
RNN / LSTM ประมวลผลตามลำดับเวลาทีละจุด สะสม hidden state เก่งเรื่อง sequential dependency ระยะไกล เทรนช้า (ขนานตามเวลาไม่ได้), เสี่ยง vanishing gradient เมื่อสัญญาณยาว 1000 sample ไม่เลือก — ยังไม่ได้ทดลองจริง เหตุผล: diagnostic feature ของ ECG เป็น local shape เป็นหลัก ไม่ใช่ long-range sequence
Transformer (self-attention) attention มองทุกจุดในสัญญาณพร้อมกัน ไม่มี locality bias ในตัว จับ context ทั้งเส้นได้ดีที่สุดทางทฤษฎี เป็น SOTA บน dataset ขนาดใหญ่ ต้องการข้อมูลจำนวนมาก (มักเป็นแสน-ล้าน) ถึงจะไม่ overfit เพราะไม่มี inductive bias ช่วยตั้งแต่ต้น ไม่เลือก — ยังไม่ได้ทดลองจริง เหตุผล: ข้อมูลที่มี (17,418 records) น้อยกว่าสเกลที่ transformer ต้องการมาก
2D-CNN บน Spectrogram แปลงสัญญาณ 1D เป็นภาพ time-frequency ก่อน แล้วใช้ CNN 2D (ต่อยอดจาก pretrained image model ได้) ใช้ transfer learning จากโมเดลภาพที่มีอยู่แล้วได้ เสีย temporal resolution จากขั้นตอนแปลงเป็นภาพ เพิ่ม preprocessing ที่ไม่จำเป็น ไม่เลือก — สัญญาณเป็น 1D อยู่แล้ว ไม่มีเหตุผลต้องแปลงเป็นภาพก่อน
Q1ทำไมใช้ CNN ไม่ใช้ LSTM หรือ Transformer?
ตอบตรง ๆ ก่อน

ยังไม่ได้ train LSTM/Transformer ขึ้นมาเทียบ empirical จริง ในโปรเจกต์นี้ — การเลือก CNN เป็นเหตุผลเชิงออกแบบ (design rationale) ไม่ใช่ผลการทดลองเปรียบเทียบสถาปัตยกรรม ต้องตอบให้ตรงถ้ากรรมการถามลึกกว่านี้

เหตุผลที่เลือก:

  • ลักษณะเฉพาะที่วินิจฉัยได้ (QRS shape, ST-segment) เป็น local pattern ที่มีรูปร่างเหมือนเดิมไม่ว่าจะเกิดขึ้นช่วงไหนของสัญญาณ 10 วินาที (translation invariance) — ตรงกับจุดแข็งของ convolution ที่ใช้ weight เดียวกันสแกนทั้งเส้นสัญญาณ ต่างจาก LSTM ที่ประมวลผลตามลำดับเวลาและเหมาะกับ dependency ระยะไกลมากกว่า
  • ข้อมูลที่มี (17,418 records) เหมาะกับโมเดลพารามิเตอร์น้อยอย่าง CNN มากกว่า — Transformer ต้องการข้อมูลจำนวนมากกว่านี้มากถึงจะไม่ overfit เพราะไม่มี inductive bias เรื่อง locality มาช่วยตั้งแต่ต้น
  • CNN เบา export เป็น ONNX รันบน backend ได้เร็วพอสำหรับใช้งานจริงแบบใกล้เคียง real-time
Q2การทดลอง 44 รอบที่พูดถึงบ่อย ๆ คือเปรียบเทียบอะไร?
จุดที่มักเข้าใจผิด ต้องตอบให้ชัด

44 รอบนี้ไม่ใช่การเปรียบเทียบสถาปัตยกรรม เป็นการทดลองแบบ data-scaling sweep — เทรน CNN สถาปัตยกรรมเดียวกันซ้ำ 44 ครั้ง โดยเพิ่มขนาดชุดข้อมูลเทรนทีละ 500 records (500 → 21,418 records) บวกอีก 1 รอบด้วยข้อมูลเต็มชุด เพื่อวัดว่า performance เปลี่ยนตามปริมาณข้อมูลอย่างไร ทุกรอบใช้ 6 epochs เท่ากัน ต่างกันแค่ขนาดข้อมูล

ผลลัพธ์จริง: val macro-AUC ขยับจาก 0.8619 (n=390) ไปถึง 0.9245 (n=17,418 เต็มชุด) — พิสูจน์ว่าปริมาณข้อมูลมีผลต่อความแม่นยำจริง เป็นเหตุผลที่ตัดสินใจใช้ข้อมูลเต็มชุดในโมเดล production ไม่ใช่หยุดที่ subset เล็ก ๆ

Q3ทำไมใช้ BCEWithLogitsLoss ไม่ใช่ CrossEntropy ธรรมดา?

เพราะ ECG 1 เส้นอาจมีความผิดปกติซ้อนกันได้มากกว่า 1 อย่างพร้อมกัน (multi-label ไม่ใช่ multi-class ที่เลือกได้คำตอบเดียว) — BCEWithLogitsLoss ให้แต่ละคลาสตัดสินอิสระต่อกัน และใส่ pos_weight ถ่วงน้ำหนักคลาสที่หายาก (เช่น MI, AFIB มีเคสน้อยกว่า NORM มาก) ป้องกันโมเดลเอนเอียงไปทายคลาสที่เจอบ่อยอย่างเดียว

EP-PINN + CardiacLocalizer

ตารางเปรียบเทียบแนวทางที่พิจารณา (3D Source Localization)

เช่นเดียวกับตารางก่อนหน้า — เป็นเหตุผลเชิงออกแบบ ไม่ใช่ ablation study ที่รันจริงในโปรเจกต์นี้

แนวทางหลักการจุดแข็งจุดอ่อน/ข้อจำกัดผลต่อการตัดสินใจ
PINN (EP-PINN)
เลือกใช้จริง		 Neural network + physics loss (Aliev–Panfilov PDE residual) บังคับคำตอบให้ไม่ขัดฟิสิกส์ ทำนายสอดคล้องชีวฟิสิกส์แม้ข้อมูลเทรนจำกัด/เป็นข้อมูลจำลอง พารามิเตอร์ฟิสิกส์ (a, k, D) ตีความได้ เทรนช้ากว่าปกติ (ต้องคำนวณ PDE residual ทุก step) ปรับน้ำหนัก loss แต่ละเทอมยาก เหมาะกับสถานการณ์จริงของโปรเจกต์: มีแต่ข้อมูลจำลอง ต้องพึ่งฟิสิกส์ช่วยควบคุมไม่ให้โมเดลเดามั่ว
Plain NN (data-only) เรียนจากคู่ข้อมูล input→output ตรง ๆ ไม่มี physics constraint เทรนเร็วกว่า ปรับแต่งง่ายกว่า เสี่ยงทำนายค่าที่ขัดกับความเป็นจริงทางชีวฟิสิกส์เมื่อข้อมูลน้อยหรือไม่ครอบคลุมทุกกรณี ไม่เลือก — ไม่มีกลไกป้องกันคำตอบที่ผิดธรรมชาติทางฟิสิกส์
Classical inverse-problem solver (เช่น boundary-element / dipole fitting) แก้สมการฟิสิกส์ตรง ๆ ด้วยวิธี numerical แบบดั้งเดิม ไม่ใช้ machine learning ไม่ต้องเทรนโมเดล ตีความผลลัพธ์ได้ตรงไปตรงมาที่สุด ต้องคำนวณ mesh ละเอียดใหม่ทุกเคส ใช้เวลานานต่อเคส ไม่เก็บ "ความรู้" ข้ามเคสเหมือนโมเดลที่เทรนแล้ว ไม่เลือก — ต้องการความเร็วพอใช้งานได้จริงกับผู้ป่วยหลายเคสต่อวัน
Q4ทำไมใช้ PINN ไม่ใช้ Neural Network ธรรมดา?
เหตุผลเชิงทฤษฎี ไม่ใช่ ablation study

PINN บังคับให้คำตอบที่โมเดลทำนายต้อง "ไม่ขัดกับสมการฟิสิกส์" (Aliev–Panfilov) โดยใส่ residual ของสมการเข้าไปเป็นส่วนหนึ่งของ loss function โดยตรง (data loss + PDE residual + initial condition + boundary condition) — สำคัญมากเมื่อข้อมูลเทรนเป็นข้อมูลจำลอง (simulated) ที่มีจำนวนจำกัดและไม่ครอบคลุมทุกกรณี สมการฟิสิกส์ทำหน้าที่เหมือนตัวควบคุม (regularizer) ป้องกันโมเดลเรียนรู้ pattern ที่ขัดกับชีวฟิสิกส์จริง

ยังไม่มีการทดลอง ablation เทียบ plain-NN (ไม่มี physics loss) กับ PINN บน benchmark เดียวกันในโปรเจกต์นี้โดยตรง — เป็นเหตุผลทางทฤษฎีที่มีงานวิจัยรองรับกว้างขวาง (Raissi et al. และงาน PINN ทางการแพทย์อื่น ๆ) แต่ไม่ใช่ตัวเลขเปรียบเทียบที่วัดเองในโปรเจกต์

Q5EP-PINN กับ CardiacLocalizer ต่างกันยังไง ทำไมมี 2 โมเดล?

คนละโมเดล คนละหน้าที่ — CardiacLocalizer ไม่มี physics loss เทรนด้วย MSE(transmembrane potential) + cross-entropy(ตำแหน่ง source) ตรง ๆ ผ่าน dilated temporal convolution encoder ส่วน EP-PINN ใส่ physics constraint เต็มรูปแบบตามที่อธิบายใน Q4 — ใช้ทั้งคู่ร่วมกันเพื่อให้ผลลัพธ์ทั้งแม่นยำเชิงตำแหน่ง (จาก CardiacLocalizer) และสอดคล้องกับฟิสิกส์ (จาก EP-PINN)

ในโค้ดมีร่องรอยว่าเคยปรับสถาปัตยกรรม CardiacLocalizer มาก่อน (เก็บ legacy encoder ไว้สำหรับโหลด checkpoint รุ่นเก่าให้ใช้งานได้ต่อ) แต่ไม่มีไฟล์ผลเทียบตัวเลขระหว่างรุ่นเก่า-ใหม่บันทึกไว้ในระบบ — ถ้าถามตรงนี้ ตอบตรง ๆ ว่ามีการอัปเดตสถาปัตยกรรมแต่ไม่มีรายงานเปรียบเทียบอย่างเป็นทางการ

สรุปจุดยืนถ้าโดนถามตรง ๆ ว่า "เทียบกับโมเดลอื่นหรือยัง"

คำตอบมาตรฐานที่ควรใช้

"ยังไม่ได้ทำการทดลองเปรียบเทียบสถาปัตยกรรมอื่นแบบ empirical โดยตรงในโปรเจกต์นี้ การเลือก CNN สำหรับ classifier และ PINN สำหรับ localization มาจากเหตุผลเชิงทฤษฎีที่มีงานวิจัยรองรับ บวกกับข้อจำกัดด้านขนาดข้อมูลและ compute ที่มีจริง — สิ่งที่ทดลองแล้วและมีตัวเลขจริงรองรับคือผลของขนาดข้อมูลต่อความแม่นยำ (44-step sweep, AUC 0.86→0.9245) การเปรียบเทียบสถาปัตยกรรมอื่นเป็นแผนงานต่อยอดที่อยากทำถ้ามีเวลาและทรัพยากรเพิ่ม"
